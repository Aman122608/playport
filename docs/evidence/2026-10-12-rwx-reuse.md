# 2026-10-12: an RWX page reused at once between x86-64 threads

**Linear:** [PLA-228](https://linear.app/playportdev/issue/PLA-228), found in sweep 2.10d
([killed threads](2026-10-12-killed-threads.md#pla-226-x86-64-terminatethread)). The owner was
away. The conservative option was taken at each choice and is recorded below.

**Changes:**

- `patches/fex` 0030: on iOS, the ARM64EC free notification removes executable ranges only where
  the memory is not committed again.
- `tools/compat/probes/childabort.c`: an `rwx` phase (only when named). Four threads each
  allocate an RWX page 1,500 times, write code into it, call it and free it.

**IPA:** `Playport-26.5-4b3b3b50.ipa` (dev), sha256
`4b3b3b507cdb992ca9b2b432be13914e265d90a81008098ad959a1281005a5fa`. It was built from commit
d331108 (records in 9223798) and installed in place. Run directories are under
`$PLAYPORT_BUILD/agent-notes/sweep10f/`.

## Cause

Wine's ARM64EC `NtFreeVirtualMemory` calls FEX's `NotifyMemoryFree` before and after the free.
FEX removes the freed range's executable intervals in the call after the free.

- **Upstream FEX** takes `ThreadCreationMutex` in the call before the free and releases it in the
  call after. No other thread's allocation notification can come between the free and the
  removal.
- **The iOS port (fex-port) dropped that mutex** for `NotifyMemoryAlloc`, `Free` and `Protect`.
  It had caused an AB-BA deadlock with Wine's heap lock.
- **The race.** Once the free returns, another thread can be given the same address. That
  thread's allocation notification registers the range as executable. The first thread's
  removal then also removes the new owner's range, so its first block decodes as NOEXEC.

The three `x64-term` runs of sweep 2.10d each show this order:

1. `[vfree] … tid=A` frees the page.
2. `[jit-pool] anon RWX … tid=B` gives B the same address, then `Add SMC interval` for B.
3. `[iOS-xquery] MISS` and `NoExec instruction in entry block` on B.

In `x64-term3`, A's lookup-cache reset (a 16 MB decommit and recommit) comes between B's
allocation and B's `Add SMC interval`. The reset is most likely the code invalidation of A's
free notification, which runs just before the interval removal.

Desktop Wine 11.18 passes the same probe. It runs x86-64 code natively, without FEX.

## Fix (fex 0030)

`InvalidationTracker::InvalidateFreedInterval`, called from the ARM64EC `NotifyMemoryFree` after a
successful free on the iOS host:

- It invalidates the range's translated code, as before.
- It removes executable intervals only for the parts that `NtQueryVirtualMemory` does not report
  as `MEM_COMMIT`.
- It holds `IntervalsLock` across the query and the removal. An allocation's notification takes
  the same lock, so a later allocation registers its range after the removal.
- If the range intersects no executable interval, it makes no query. Ordinary heap frees cost
  nothing extra.
- It logs a kept range as `[iOS-xrem] kept #N …` (the first 64).

**Choices:**

- **The mutex was not restored.** A lock held across the free could bring back the AB-BA
  deadlock the port removed. The fix takes no new lock and adds no lock order.
- **The removal was not moved to the call before the free.** That call has the caller's size
  (0 for `MEM_RELEASE`). A failed free would also need its range re-registered.
- **WoW64 (i386) is unchanged.** It still holds `ThreadCreationMutex` across the free.
- **Cross-process notifications get the same check.** These are queued and run later, so their
  memory may also be reused by then.

## Follow-ups

- **An execute fault at the start of a page reads below the page.** While such a fault is
  dispatched, ARM64EC native code reads the bytes just below the faulting address. If that page
  is unmapped, the read faults again and the process ends. Seen once, in `base-rwx`, with the race.
  Any execute fault at a page start after an unmapped page may hit it; not checked further.
- **`NotifyMemoryProtect` has the same window**, between the protect and its notification. It
  matters only when another thread changes the same page, which a program does not normally do.
  It was not changed.
