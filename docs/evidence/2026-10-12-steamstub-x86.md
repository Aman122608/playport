## What Madeira does

Madeira (`upstream/madeira`, read only) has no SteamStub code. Its route to a Steam game is the
real Steam client inside the prefix (the "Steam Testing" button in
`app/Madeira/ContentView.swift`, which writes and runs `C:\steam-launch.bat` against an installed
Steam). A wrapped executable's stub then finds a running Steam and passes its check. Playport runs no
Steam client in the prefix: its Steam session is native, and games get the Steam API emulator
(`SteamAPISwap`). With no client, the stub's check fails and the game exits. That is what PLA-99's
titles did, after `steamstub: <exe>: SteamStub 3.1 x86 is not supported yet`. Letting the stub
run (the first option) would need a Steam client in the prefix, so the stub is taken off instead
(the second option).

## Design

- Variant 3.1 has one 0xF0-byte header layout for x86 and x64 (`SteamStub.Header31`). After the
  XOR-chain decode it gives the image base (0x08), the original entry point (0x20), the app ID
  (0x38), the flags (0x3C), the encrypted code section's RVA (0x48) and size (0x50), its AES-256
  key (0x58), the IV (0x78) and the code's first ciphertext block (0x88).
- **The entry point** is read as an RVA. When that is not in an executable section, it is read as
  an address in the header's image base. When neither works, the stub is reported as not removable,
  and the file is left alone.
- **Encrypted code** is the header naming a code section with the no-encryption flag (0x02) clear.
  The section in the file starts with the second ciphertext block, because the first is kept in the
  header. The plain code is AES-256-CBC over that block followed by the section's bytes, for the
  header's size. The IV is the header's IV, decrypted with the key as one ECB block. The size must
  be a multiple of 16 that fits the section, and the RVA must be the section's start. Otherwise the
  stub is reported (`Info.defect`) and the file is left alone. Bytes past the size stay as they
  were. The AES is ContentKit's `AES256Decryptor`, already used for depot chunks.
- **x86 keeps `.bind`.** Only the entry point changes, and the unused stub section stays: the
  relocations of an x86 stub may sit in a section before it. x64 behaves as before (`.bind` is
  dropped when it is last and unreferenced).
- **3.0 stays unsupported**, reported as `SteamStub 3.0 <arch> is not supported yet`.
- The log line names the encryption: `steamstub: <exe>: SteamStub 3.1 x86 with encrypted code,
  removed`. Games keep their `.orig` and restore as before.

## Host tests

`./pp test --swift SteamClient`: 191 tests, 0 failures, 1 skipped (the `STEAMSTUB_SAMPLE`
real-sample test). New and changed `SteamStubTests`:

- a 3.1 x86 image is read (app ID, entry point, flags) and unwrapped, keeping `.bind`;
- an entry point given as an image-base address is read as an RVA, and a bad one is refused;
- encrypted code is decrypted, x64 and x86, against a known answer made with OpenSSL
  (`openssl enc -aes-256-cbc -nopad` for the code and `-aes-256-ecb` for the header's IV);
- the no-encryption flag leaves the code as it is;
- an encrypted size that does not fit its section, and 3.0 x86/x64, are refused.

The real-sample test is skipped: no real x86 or encrypted executable was available (below). With
`STEAMSTUB_SAMPLE` set it no longer requires `.bind` to be gone on x86.

## Open

- A real check: Castle Crashers (x86), Curse of the Moon (x86) or Tetris Effect (x64, encrypted),
  or any other 3.1 x86 or encrypted title from the library, on the phone. On the host, set
  `STEAMSTUB_SAMPLE=<exe> ./pp test --swift SteamClient --filter testARealSample`.
- If a real encrypted title starts but crashes at once, suspect the first 16 bytes of its code
  section first: the IV is the one part of the format that only those bytes depend on.
- A stub entered through a TLS callback rather than the entry point is not found. This was already
  the case before this change.
