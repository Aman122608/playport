## i386 IL-only executables (PLA-154)

**Cause 1: the window refused the image's COM+ flags.** `hello32.exe` (PLA-125's test program,
`mcs -platform:x86`: PE32, Machine `0x14c`, COR flags `ILONLY | 32BITREQUIRED`) is an ordinary
i386 image to Wine: the server sets `IMAGE_FLAGS_ComPlusILOnly` and, because 32BITREQUIRED is set,
not `ComPlusNativeReady`. The WoW64 window's image route (`ios_wow64_section_bounds`,
madeira-unix 0059) accepted only `ImageMappedFlat` and `ImageDynamicallyRelocated` and returned
`STATUS_NOT_SUPPORTED` for anything else: `virtual_map_main_module = 0xc00000bb`. Wine Mono's
own assemblies (AnyCPU, so `ILOnly | NativeReady`) would have been refused the same way when
Mono loads them as images. Madeira-unix 0112 accepts the three COM+ flags; Wine's i386 loader
maps such images as i386 too (only a 64-bit process converts an AnyCPU image to PE64). Host
test: `build/wow64/section_test.c` maps an image with all three flags at a fixed guest base
(it fails without the patch at the new assertion).

**Cause 2: an atomic store's fault was raised as a read.** With 0112 (`run-mono32`, IPA
c6e72b28), the image mapped, Mono started (`libmono-2.0-x86.dll`, `mscorlib.dll`,
`System.Windows.Forms.dll` mapped into the window) and the process died 565 ms later:

```
[exc-disp] raise tid=002c code=c0000005 flags=0 addr=0x128c6de14 pc=128c6de14 nparams=2 p0=0 p1=703b0e3484
002c:err:wow:call_user_exception_dispatcher Playport: i386 exception c0000005 at eip 7a7d6b68 (00000000 02793484): ...
session: title 1: ended, exit code c0000005 after 565 ms
```

Guest `0x2790000` was a 64 KiB RWX region holding Mono's freshly compiled code (`55 8b ec …`),
which FEX keeps read-only to catch self-modifying writes: seven plain stores into it were
"Handled self-modifying code". The eighth was an LSE atomic (`0xb8e482a4`, an x86 `lock`
instruction patching a call) with ESR `0x9200004f` (WnR=1), but the SIGBUS path labels the
direction from the opcode, where bit 22 means "load" and is the atomic's acquire bit: the fault
went out as a read, which FEX does not service. Madeira-unix 0113 also takes the data abort's
ISS.WnR (not for cache maintenance).

**After both** (`run-mono32b`, `run-mono32-shot`, IPA 747b8991):

```
title: +4.40 s first window
session: title 1: ended, exit code 2a after 31210 ms
```

The pulled `hello-result.txt` reads `Hello from .NET 4.0.30319.42000 on 6.13.0 (tarball), 32-bit
process, Microsoft Windows NT 10.0.19045.0`; the screenshot 10 s after Play shows the WinForms
window "Wine Mono test" with that line. The run took 2,464 FEX self-modifying-code faults (one
per store into a code page FEX protects); pool at the end `head_mb=27 tail_mb=161 room_mb=325
exhausted=none`.

## DXSETUP's managed DirectX check (PLA-170)

**Desktop first.** The Jun2010 redistributable (`_CommonRedist/DirectX/Jun2010` from Steamworks
Shared) under Proton 10 in a scratch prefix, `DXSETUP.exe /silent`, one change per run:

| Run | Prefix | DirectX.log | Exit |
| --- | --- | --- | --- |
| a | Proton's own | `Installation ended with value 0 = Installation succeeded` | 0 |
| b1 | a, without `Microsoft.NET\Framework\v*\fusion.dll` | `CFusion::CFusion(): LoadLibraryShim() failed, error = 0x80070006`, `-9` | 247 |
| b2 | a, the 32-bit view's `InstallRoot` set to `…\Framework64\` | the same | 247 |
| b3 | a, the 32-bit view's `InstallRoot` deleted | the same | 247 |

Proton's prefix gets `Microsoft.NET\Framework\v1.1.4322|v2.0.50727|v4.0.30319\fusion.dll` (and the
rest of Wine Mono's `support/dotnetfakedlls.inf`) as links to its `i386-windows` builtins, and
`Framework64\…` to `x86_64-windows`; its `Wow6432Node\Microsoft\.NETFramework` says
`InstallRoot=C:\windows\Microsoft.NET\Framework\`. Run b1 reproduces the phone's log exactly.
On the phone both are missing: decision 0077 left the fake directories out, and the prefix has
no `Software\Wow6432Node`, so an i386 `mscoree` reads the 64-bit view's `…\Framework64\`, where an
i386 process cannot load the 64-bit `fusion.dll` (run b2). `LoadLibraryShim` builds
`<InstallRoot><version>\fusion.dll` and returns `E_HANDLE` (0x80070006) when that fails.

**Fix** (decision 0085): the session links the inf's sections into the prefix
(`dotnet: 32 links (32-bit [FakeDlls] 16, 64-bit [FakeDlls64] 16), 0 lines skipped`), and
wine-pe 0036 gives a WoW64 process the `Framework\` directory where the value names
`Framework64\`.

**Phone** (`cc-install`, `cc-play`: Castle Crashers Demo installed, then Play; decision 0083
reran the failed record, decision 0084 restarted before the game):

```
002c:err:wow:wow64_NtMapViewOfSection Playport: i386 image C:\windows\Microsoft.NET\Framework\v2.0.50727\fusion.dll at 7a280000
dxupdate: DirectXUpdateInstallPlugIn(): Installing: d3dx9_24_x86.inf - [x64_install]
dxupdate: Installed file C:\windows\SysWOW64\d3dx9_24.dll
dxupdate: InstallEXE(): Command:	infinst.exe d3dx9_24_x64.inf
dxupdate: InstallEXE(): infinst.exe returned -1073741800.
dsetup32: Installation ended with value -1073741800 = Unknown error
title: prerequisite: Steam dxsetup (…) exit 0xc0000018 after 5 s; recorded for … by build 984d70b908d878d7 (a failure: the game starts anyway; a new build runs it again)
```

The managed DirectX check now passes (fusion loads from `Framework\v2.0.50727`) and DXSETUP
installs the first x86 cab. It stops at the first x64 cab: its `infinst.exe` is x86-64,
relocations stripped, ImageBase `0x100000000`, SizeOfImage `0x10000` (characteristics `0x23`,
checked on the extracted file), and iOS refuses that base:

```
0034:err:virtual:map_fixed_area out of memory for 0x100000000-0x100010000
[exe-base] 0x100000000+0x10000 refused with nothing mapped there (status 0xc0000017)
wine: failed to create main module for L"C:\\windows\\temp\\DX9A50.tmp\\infinst.exe", status c0000018
```

So the HasRunKey is not written yet; the residual cause is the fixed 4 GiB base, outside the
executable window that holds `[0x140000000, 0x15c000000)` for such executables
([ARCHITECTURE](../ARCHITECTURE.md#jit-pool-placement), [evidence](2026-10-07-executable-window.md)). Castle Crashers Demo still reached its
first frame at +4.25 s after the restart (the "Featured programmer" credits screen).

**The native DLLs DXSETUP copied.** It replaced `syswow64\d3dx9_24.dll` with Microsoft's file.
After the restart's launch request, `link_system32` had put the builtin back (AFC `stat`):
`syswow64/d3dx9_24.dll` is `S_IFLNK` to `S1Probe.app/i386-windows/d3dx9_24.dll`, and
`system32/d3dx9_24.dll` and `syswow64/d3dx9_43.dll` link to the bundle too. Under Proton the
native file stays but Wine's load order picks the builtin for a Microsoft-signed system DLL;
here the link replaces it, and the result (the builtin loads) is the same.

## Limits

- No XNA title was tried: none was identified in the owner's library list
  (`agent-notes/speedrun/library.tsv` names no engine, and no triage note marks one).
- Mono's JIT under FEX in an i386 process faults once per store into a code page (2,464 for the
  test program); a large .NET game may start slowly. Not measured.
- The rewrite in wine-pe 0036 covers mscoree only; any other i386 reader of a key that differs
  between the two registry views still gets the 64-bit value (decision 0085).
